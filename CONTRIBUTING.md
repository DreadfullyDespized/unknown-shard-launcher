# Contributing

## Repo label: TEST

**TEST.** Verified work (issue → PR → QA checklist run → grader ≠ doer review) merges to `main` promptly; PRs must not sit unmerged once verified. Dread tests `main` builds afterward. Fixes found in testing go back through the same flow (new issue → PR → merge). Tracked by the GitHub topic `tier-test`.

## Process

1. Open an issue first: problem, evidence, acceptance criteria.
2. Branch `cursor/<issue#>-<slug>`; never commit directly to `main`.
3. One scoped PR per issue with `Closes #<issue>`, what, why, test plan and results, risk/rollback.
4. Never skip checks; no force-push to shared branches.
5. Review by someone other than the author.

## Grader check and correction loop

- **`grader` must be green before merge.** The `grader` check fails by default. It passes only when the latest valid verdict on the PR has the first line `Verdict: PASS <full 40-character head SHA>` and a line `grader-run: gr-YYYYMMDDTHHMMSSZ-<16 hex>` from a fresh `python3 tools/correction_loop/grader.py new-run-id` (one ID per grader session, never reused, dated after the head commit and within 24 hours of the verdict), posted by a non-bot login in `grader_logins` (DreadfullyDespized, the PR author included), and the PR is at least 30 minutes old. Any push makes the old PASS stale. Rules: `docs/correction-loop.md`.
- **Correction issues:** a failed watched workflow on `main`, a failed deployment, a `Verdict: FAIL` line, the `dread-correction` label, a `/correction` comment or `gh workflow run correction-intake.yml -f kind=correction -f target="<title>"` opens an issue labeled `correction`. It stays closed only when it links a merged PR whose `## For Dread` has its own `**Level:** 1` (codebase) or `**Level:** 2` (lint/CI) line before Proof.
- **Issues:** open them with the Bug, Improvement or Feature form in `.github/ISSUE_TEMPLATE/`.
- Details and settings: `docs/correction-loop.md`, `tools/correction_loop/config.json`.

## Public repo rule

This repository is public. Never commit server addresses, ports, IPs, patch URLs, keys, secrets or internal paths. Server-specific values are supplied at build time from a private config (see `launcher.build.example.props` once the launcher code lands).

**No code comments (Dread 2026-10-04):** the `No comments` step of the gate job (`tools/check_no_comments.py`) fails any PR that adds a comment line; names and structure carry the meaning instead. Only these machine directives pass: line-1 shebang, Python encoding cookie, `# type: ignore[…]`, `# noqa[: codes]`, `# shellcheck disable|enable|shell|source=…`, `# yaml-language-server: …`, PowerShell `#Requires -…`, bare `// eslint-disable|enable[-next-line|-line] [rules]` or `/* eslint-disable|enable [rules] */` (no `--` prose), `// @ts-expect-error`, `// @ts-nocheck`, `/// <reference … />`, `// <auto-generated>`. Vendored and generated paths are exempted by the global list in the script; repo-specific exempt paths, directives and self-test cases live in `tools/no-comments.json`, so the script itself is byte-identical in every repo; run `python3 tools/check_no_comments.py --base origin/main` locally before pushing.

## Agent guardrails

Everything an agent needs is in this file and the checks it names; no seat memory is required.

- **PR body:** the `PR body` step of the gate job (`tools/check_pr_body.py`) requires:
  - `## For Dread` with all four fields filled in: **Ask:**, **What changes for you:**, **Proof:**, **NOT done:**. **Proof:** needs at least one link, and every github.com `blob/` or `tree/` link in it must be pinned to a 40-hex commit SHA, not a branch. Run, PR, issue and commit URLs are fine.
  - a non-empty `## Blast radius` (what the change can touch and what it cannot).
  - on bug or correction PRs (a label containing the word `bug` or `correction`, or a title starting with `fix:`), also `## Root cause`, `## Regression origin` and `## Options` with at least 2 options (list items or `###` headings), each with an evidence link.

  A section or field fails if it holds a placeholder word anywhere (`TBD`, `TBA`, `TODO`, `FIXME`, `WIP`, "fill in", "to be determined"), is only `N/A`/`None`, or is only a `Closes #N` line. Headings inside HTML comments or code fences don't count. Quoting a placeholder in backticks inside otherwise real text is fine. Start from `.github/pull_request_template.md`.
- **No comments:** the `No comments` step fails any added comment line; only the machine directives listed above pass. It also scans fenced code blocks in Markdown that carry a language tag (`sh`, `bash`, `powershell`, `python`, `js`, `ts`, `yaml`, `cs` and more), so put notes about a command in the prose around the block, not after a `#`.
- **QA floor is FAIL:** every claim counts as FAIL until it is proven with linked evidence (CI run URL, commit, log or test output). "Tested" without a link is a FAIL.
- **Escaped bugs:** every bug found after merge adds a test case (unit, self-test or validator case) in the fix PR, one that would have caught it.
- **Public repo:** never commit server hostnames, IPs, ports, URLs or keys (see the Public repo rule).
- **Run the checks locally before pushing.** The repo-wide checks, using a PR body saved as `pr-body.md`:

```sh
python3 tools/check_no_comments.py --self-test && python3 tools/check_no_comments.py --base origin/main
python3 tools/check_pr_body.py --self-test && python3 tools/check_pr_body.py --body-file pr-body.md --title "<PR title>" --labels "<label,label>"
```

  The launcher builds and tests with the .NET 8 SDK, the same commands as the `CI` workflow:

```sh
dotnet build ShardLauncher.sln -c Release
dotnet test ShardLauncher.sln -c Release --no-build
```

## CI minutes: one gate job, a pre-push hook, batched pushes

Each GitHub-hosted job bills at least one full minute, even when it finishes in 5 seconds, so five tiny check jobs used to bill five minutes on every push.

- **One gate job.** Every PR push runs ONE job, `.github/workflows/gate.yml` (check name `grader`). It has one step per check, run in order: workflow lint, No comments, PR body, correction-loop tests, then the grader verdict. Every step runs even when an earlier one fails, and any failed step fails the job. The step names in the run log tell you which check failed. Build and test CI for the code itself stays in its own workflow.
- **Install the pre-push hook once:** `sh tools/hooks/install`. After that, `git push` runs `tools/hooks/pre-push`, which runs the same steps locally and blocks the push when one fails. It needs `python3` with PyYAML (`python3 -m pip install pyyaml==6.0.2`). It checks the PR body with `gh pr view` when the PR exists, or the file named by `PR_BODY_FILE`. Set `GATE_BASE` to compare against a base other than `origin/main`. The grader verdict is the one step that only runs on GitHub, because the verdict has to name the head you just pushed.
- **Batch your commits.** Commit locally as often as you like, but push once per finished change that is green locally. Every push to a PR branch bills a gate minute plus any build CI. Do not push a fix one line at a time to see whether CI passes. Run the hook instead. Write the PR body from `.github/pull_request_template.md` before you open the PR, because each body edit re-runs the gate. Labels no longer trigger runs, so after you add a `bug` or `correction` label, push or edit the body to re-check.
- **Early grader PASS:** the relay never sleeps on a runner. If a PASS lands before the PR is 30 minutes old, comment `/grader` on the PR after the eligible time it reports.
- **Workflow rules (level 2):** `tools/check_workflows.py` is byte-identical in every repo and runs in the gate. It fails when more than one gate-type job runs on `pull_request`, a job has no `timeout-minutes`, a workflow triggers on PR `labeled`/`unlabeled`, a step sleeps longer than 30 seconds, or a hosted job uses anything but `ubuntu-latest`. Run `python3 tools/check_workflows.py --self-test && python3 tools/check_workflows.py` after you touch a workflow, and use `actionlint` too.
